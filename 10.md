# Задание 10. «Электронная очередь без драки»

Разработайте сервис электронной очереди.

Посетитель получает талон и ожидает вызова. Несколько операторов одновременно обслуживают одну общую очередь. Каждый оператор может вызвать следующего посетителя, завершить обслуживание либо пропустить вызванный талон.

Главное требование системы:

> Один талон не должен одновременно попасть к двум операторам.

Система должна корректно работать при конкурентных запросах нескольких операторов.

---

## 1. Основной сценарий

Посетители получают талоны:

```text
A001
A002
A003
A004
A005
```

Очередь:

```text
A001 → A002 → A003 → A004 → A005
```

Работают три оператора:

```text
Оператор 1
Оператор 2
Оператор 3
```

Операторы практически одновременно запрашивают следующего посетителя.

Корректный результат:

```text
Оператор 1 → A001
Оператор 2 → A002
Оператор 3 → A003
```

Недопустимый результат:

```text
Оператор 1 → A001
Оператор 2 → A001
```

Даже если запросы поступили одновременно.

---

## 2. Получение талона

Пользователь должен иметь возможность получить новый талон.

Например:

```text
POST /tickets
```

Ответ:

```json
{
  "id": "a132aabb",
  "number": "A017",
  "status": "waiting"
}
```

Номер талона должен быть уникальным в рамках используемой модели очереди.

Минимальный формат:

```text
A001
A002
A003
...
```

Допускается другой формат.

---

## 3. Состояния талона

Каждый талон должен иметь состояние.

Минимальный набор:

```text
waiting
serving
completed
skipped
```

### waiting

Посетитель ожидает своей очереди.

### serving

Талон уже забрал конкретный оператор и сейчас обслуживает посетителя.

### completed

Обслуживание успешно завершено.

### skipped

Посетитель был вызван, но обслуживание не состоялось.

Основные переходы:

```text
             ┌→ completed
waiting → serving
             └→ skipped
```

Переход напрямую:

```text
waiting → completed
```

не допускается.

---

## 4. Операторы

В системе должно существовать несколько операторов.

Для оператора необходимо хранить минимум:

```text
id
name
```

Например:

```text
operator-1
operator-2
operator-3
```

Одновременно несколько операторов могут выполнять запрос:

```text
вызвать следующего
```

---

## 5. Вызов следующего посетителя

Оператор должен иметь возможность запросить следующий ожидающий талон.

Например:

```text
POST /operators/{operatorId}/next
```

Сервис должен:

1. найти следующий талон со статусом waiting;
2. закрепить его за оператором;
3. перевести талон в serving;
4. вернуть его оператору.

Пример:

```json
{
  "number": "A017",
  "status": "serving",
  "operatorId": "operator-2"
}
```

Если очередь пуста, API должно корректно сообщить об этом.

Например:

```text
204 No Content
```

или другой обоснованный вариант.

---

## 6. Главное требование конкурентности

Представим очередь:

```text
A001
A002
A003
```

В один момент времени два оператора выполняют:

```text
POST /operators/1/next
POST /operators/2/next
```

Недопустима реализация:

```text
1. найти первый waiting
2. вернуть его
3. потом изменить status
```

Потому что может произойти:

```text
Operator 1: SELECT A001
Operator 2: SELECT A001

Operator 1: A001 → serving
Operator 2: A001 → serving
```

Оба оператора получили один талон.

Операция:

```text
найти следующий свободный талон
+
закрепить его за оператором
+
перевести в serving
```

должна выполняться как единая конкурентно безопасная операция.

То есть система должна обеспечивать:

```text
claim(ticket)
```

При успешном захвате конкретного талона другим операторам он больше недоступен.

Способ обеспечения этой гарантии необходимо выбрать самостоятельно и объяснить на защите.

---

## 7. Порядок очереди

По умолчанию используется FIFO:

```text
первым пришёл
→ первым обслуживается
```

Например:

```text
A001 created 10:00
A002 created 10:01
A003 created 10:02
```

При последовательных вызовах должны выдаваться:

```text
A001
A002
A003
```

Если несколько операторов забирают талоны конкурентно, каждый должен получить свой талон из начала очереди.

---

## 8. Один оператор — один активный талон

Оператор не должен одновременно обслуживать несколько посетителей.

Если:

```text
operator-1 → A001 → serving
```

и оператор снова выполняет:

```text
POST /operators/operator-1/next
```

система не должна выдавать ему A002, пока A001 не завершён или не пропущен.

Таким образом:

```text
operator
   |
   └── максимум один serving ticket
```

---

## 9. Завершение обслуживания

Оператор должен иметь возможность завершить текущий талон.

Например:

```text
POST /operators/{operatorId}/complete
```

После этого:

```text
serving → completed
```

Необходимо сохранить:

- время начала обслуживания;
- время завершения;
- оператора, который обслужил талон.

После завершения оператор снова может вызвать следующего посетителя.

---

## 10. Пропуск талона

Оператор должен иметь возможность отметить вызванного посетителя как пропущенного.

Например:

```text
POST /operators/{operatorId}/skip
```

Переход:

```text
serving → skipped
```

После этого оператор может вызвать следующий талон.

Повторно автоматически возвращать пропущенный талон в очередь не требуется.

---

## 11. Недопустимые переходы

Сервис должен проверять корректность операций.

Например, нельзя:

```text
waiting → completed
completed → serving
skipped → completed
completed → waiting
```

Нельзя завершить талон:

```text
operator-2
```

если он обслуживается:

```text
operator-1
```

Нельзя повторно завершить уже завершённый талон.

API должно возвращать корректную ошибку.

---

## 12. Хранение данных

Используйте постоянное хранилище.

Рекомендуется:

```text
PostgreSQL
```

Допускается другая реляционная БД при согласовании.

После перезапуска приложения должны сохраняться:

- выданные талоны;
- состояния талонов;
- операторы;
- информация об обслуживании;
- история завершённых и пропущенных талонов.

---

## 13. HTTP API

Отдельный пользовательский интерфейс разрабатывать не требуется.

Для демонстрации достаточно Swagger/OpenAPI.

Минимальный API:

```text
POST /tickets
GET  /tickets
GET  /tickets/{id}

GET  /operators

POST /operators/{id}/next
POST /operators/{id}/complete
POST /operators/{id}/skip
```

Допускается другая структура API, если она сохраняет необходимую функциональность.

---

## 14. Просмотр очереди

Необходимо предоставить возможность посмотреть состояние очереди.

Например:

```text
GET /tickets
```

Ответ:

```text
A017 waiting
A018 waiting
A019 serving operator-2
A020 completed
A021 skipped
```

Должна существовать возможность фильтрации хотя бы по состоянию.

Например:

```text
GET /tickets?status=waiting
```

---

## 15. История талона

Для каждого талона должна быть доступна информация минимум о:

```text
номер талона
время создания
текущее состояние
оператор
время начала обслуживания
время завершения
```

Например:

```json
{
  "number": "A017",
  "status": "completed",
  "createdAt": "10:14:32",
  "startedAt": "10:18:04",
  "completedAt": "10:22:51",
  "operatorId": "operator-2"
}
```

---

## 16. Конкурентный эксперимент

Необходимо отдельно доказать, что один талон невозможно выдать двум операторам.

Создайте ситуацию:

```text
100 операторов
       ↓
одновременно вызывают /next
       ↓
100 ожидающих талонов
```

После выполнения запросов необходимо проверить:

- каждый оператор получил максимум один талон;
- каждый талон принадлежит максимум одному оператору;
- один номер талона не был возвращён двум запросам;
- состояние БД осталось консистентным.

Тест должен запускаться многократно.

---

## 17. Нельзя решить только mutex в одном процессе

Если состояние хранится в базе данных, необходимо учитывать, что приложение потенциально может быть запущено в нескольких экземплярах:

```text
              Load Balancer
              /          \
             /            \
         Go instance 1   Go instance 2
              \            /
               \          /
                PostgreSQL
```

Обычный:

```go
sync.Mutex
```

защищает только память одного процесса.

Он не защищает данные от второго экземпляра приложения.

Поэтому гарантия:

> один талон может получить только один оператор

должна обеспечиваться на уровне общего состояния системы, а не только локальным mutex одного Go-процесса.

В README необходимо описать, за счёт какого механизма это гарантируется.

---

## 18. Нагрузка

Проведите эксперимент с конкурентным получением талонов.

Например:

```text
100 waiting tickets
100 concurrent /next requests
```

Затем:

```text
1000 waiting tickets
100 concurrent operators
```

Измерьте:

- сколько запросов выполнено;
- общее время;
- количество успешно выданных талонов;

- количество конфликтов или ошибок;
- появились ли дубли.

Необходимо объяснить, что происходит при росте конкурентности.

---

## 19. Что происходит под нагрузкой

При большом количестве операторов возможна ситуация:

```text
много запросов
      ↓
все хотят начало одной очереди
      ↓
конкуренция за одни и те же строки БД
```

Необходимо понимать и уметь объяснить:

- где возникает contention;
- какие операции блокируются;
- почему один талон не выдаётся дважды;
- что происходит с остальными операторами;
- как выбранное решение ведёт себя при увеличении количества конкурентных запросов.

---

## 20. Таймауты и context

HTTP-запросы должны использовать context.Context.

Операции с базой данных также должны выполняться с context.

Необходимо предусмотреть разумные timeout для операций.

Если клиент отменил запрос либо истёк timeout, приложение не должно оставлять данные в промежуточном неконсистентном состоянии.

---

## 21. Graceful shutdown

Приложение должно корректно обрабатывать:

```text
SIGINT
SIGTERM
```

При завершении необходимо:

1. перестать принимать новые HTTP-запросы;
2. дать выполняющимся запросам возможность завершиться в пределах timeout;
3. корректно закрыть соединения с БД;
4. завершить приложение.

---

## 22. Обязательные тесты

Необходимо покрыть тестами минимум следующие сценарии:

### Обычная выдача

```text
A001
A002
A003

next → A001
next → A002
next → A003
```

### Пустая очередь

```text
waiting tickets = 0
next → очередь пуста
```

### Завершение

```text
waiting
→ serving
→ completed
```

### Пропуск

```text
waiting
→ serving
→ skipped
```

### Повторный вызов оператором

```text
operator already has serving ticket
→ новый талон не выдаётся
```

### Чужое завершение

```text
operator-1 обслуживает A001
operator-2 пытается complete A001
→ ошибка
```

### Конкурентный вызов

Несколько goroutine одновременно вызывают получение следующего талона.

Необходимо доказать отсутствие дублирующей выдачи.

Проект должен проходить:

```bash
go test ./...
```

и:

```bash
go test -race ./...
```

## 23. Что не требуется

В рамках задания не требуется:

- frontend;
- экран электронной очереди;
- голосовое озвучивание номера;
- печать физических талонов;
- SMS;
- Telegram;
- авторизация;
- Kubernetes;
- Kafka/RabbitMQ;
- микросервисная архитектура;
- приоритетные очереди;
- несколько филиалов;
- предварительная запись.

Основная задача — корректная конкурентная работа одной электронной очереди.

## 25. Демонстрация

На защите необходимо показать:

1. создание нескольких талонов;
2. просмотр очереди;
3. вызов следующего посетителя первым оператором;
4. вызов следующего посетителя вторым оператором;
5. завершение обслуживания;
6. пропуск талона;
7. запрет выдачи второго талона занятому оператору;
8. запрет завершения чужого талона;
9. конкурентный вызов /next несколькими операторами;
10. отсутствие двойной выдачи;
11. результаты конкурентного теста;
12. сохранение состояния после перезапуска приложения.

Главный сценарий защиты:

```text
есть один waiting ticket

        A001
          ↑
          |
   +------+------+
   |             |
operator-1    operator-2
   |             |
   +---- next ---+
```

Два запроса отправляются конкурентно.

После их выполнения:

```text
только один оператор → A001
второй оператор      → очередь пуста
```

В базе:

```text
A001
status = serving
operator_id = только один оператор
```

Именно эту гарантию необходимо не просто реализовать, а уметь объяснить: где принимается атомарное решение о выдаче талона и почему второй конкурентный запрос уже не может получить тот же талон.
